# Contributing

Thanks for taking the time to help. This is a small project, so a few plain
rules keep reviews quick and the code easy to follow.

## You own every line you send

When you open a PR, we assume you understand every line in it. If a reviewer
asks "why is this here?", you should be able to answer without going back to
ask a tool. That goes double for the eBPF side: a wrong offset or a missing
bounds check in `agent/bpf/http.c` is easy to write and hard to spot.

So please don't send PRs that were generated by AI and pushed without real
review. If you can't explain it, don't send it yet.

## Write your own words

PR descriptions, review comments and commit messages should be written by you.
We want to hear how you think about the change, not a generated summary of it.

Using a tool to fix grammar or tidy up a sentence is fine. Just read it again
before you post and strip out the filler: the "This PR introduces a robust and
comprehensive...", the long bullet lists that repeat the diff, the emoji
headings. A couple of honest sentences beat a page of polish.

A good description answers three things:

- What changed.
- Why.
- How you tested it.

## Keep PRs small and testable

One change per PR. If you find something unrelated along the way, open a
separate PR for it.

A reviewer should be able to check your change locally. For most changes that
means:

```sh
make up
make metrics
```

and saying in the PR what you expected to see and what you saw. If your change
needs a different way to test it, write the steps down.

Big PRs sit in review for a long time and tend to hide bugs. If your change is
large, open an issue first and we can figure out how to split it.

## Before you open a PR

- It builds and runs with `make up`.
- You've read your own diff once, top to bottom.
- Commit messages say what changed and why, in your own words.
